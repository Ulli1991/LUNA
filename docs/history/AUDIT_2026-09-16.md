# LUNA code audit — 2026-09-16

Scope: the main tree at commit de8a7f6 (≈44k lines of Python), reviewed for
correctness, readability, user-friendliness, testing and software practice.

Method: six independent static reviews (hydro + sources, gravity, AMR,
ICs + cosmology + units + I/O, runners + config, tests + CI + docs + hygiene)
produced candidate findings. **Every finding below was then re-checked by me
against the code**: line ranges re-read, counts re-derived with my own scripts,
and two claims exercised on a GPU. Findings the reviewers made that I could not
confirm are listed separately in §11 and are not part of the assessment. One
reviewer claim was wrong and is recorded in §12.

Status tags: **CONFIRMED** = I can point at the line and explain the failure.
**RUN** = also reproduced on one MI300A today. **SUSPECTED** = the code pattern
is confirmed but the size of the effect needs a run.

---

## 1. Verdict

The numerical kernels are right. MUSCL-Hancock, HLLC and L-HLLC, the limiters,
the multigrid core and its isolated boundary, the implicit Poisson adjoint, the
fixed-point CIC deposit, the DM super-comoving unit chain and the AMR seam/reflux
design are formula-correct as read. The AMR and gradient test layers are
exemplary.

The problems are around the kernels, and they have one root cause: the same
piece of logic exists in several copies, and fixes reach some copies but not
others. Five ghost-fill sequences in AMR, three particle-mesh implementations,
three coupled cosmology loops, six time loops, six copies of the half-step
predictor. Every confirmed production bug in §2 is a twin that missed a fix or
a call site that did not get an argument the other call sites got.

Second cause: configuration is not a single source of truth. 365 `getattr(cfg,
name, default)` sites in library code, 11 knobs read but never declared, 25
sites whose fallback default contradicts the template, ~30 env vars read in
library code with 19 undocumented, a stale local `config.py` that silently skips
`validate()`, and no run mode that serialises its configuration.

Third: what is tested is not what runs in production. CI runs 14 of 134 test
functions. Every test forces float64. Every multi-device test runs on 8 CPU
virtual devices and skips on a real 2- or 4-GPU node. No test drives the
standard dense runner, the multi-GPU DM blocks loop, sharded AMR with regridding,
or any restart.

None of this is unusual for a research code at this stage, and it is fixable in
weeks, because the kernels underneath are right. But the paper's claims need to
match what the code guarantees today, and §8 lists where they do not.

### The 8 GPU / 1024^3 FP64 failure is the DOCUMENTED uint32 offset wrap

Job 11806287 died with a non-finite dt at step 9, the rerun (11811258) at step
5. Not new, not a regression. `docs/history/JUPITER.md:44`, written 2026-08-06: a
(5, 512^3) FP64 state puts field 4 at byte offset 4*512^3*8 = 2^32 EXACTLY,
which wraps to field 0 in the 32-bit shift-based indexing XLA emits for
power-of-two strides, silently corrupting the PLM y-fluxes at the blast. That
entry ends: "Check 512^3 per-GPU shards at >=8 GPUs before any fp64 plain-path
ladder run." That is exactly this configuration. Its listed workarounds are
recon32, the fused kernel, and a non-power-of-two tile. The 2026-09-18
variants agree with all three:

| kernel | precision | result | Mcell/s |
|---|---|---|---|
| default (`hydro_fused=False`) | FP64 | non-finite dt at step 5 / step 9 | - |
| fused 2-ghost | FP64 | 30 steps clean | 7 987 (998/GPU = the FP64 roofline) |
| default | FP32 | 30 steps clean | 17 880 (July: 18 134) |

So the FP64 weak ladder on this tree is 1 GPU 1 087 / 8 GPU 7 987 (fused) /
64 GPU 63 906, i.e. 92% weak efficiency, and the FP32 8-GPU point is
unchanged. The July "8-GPU baseline 18 134" was FP32, not FP64.

OPEN AND IMPORTANT: the wrap corrupts SILENTLY; the Jupiter note says the
non-finite gate catches it only when the wrong fluxes happen to drive a
density negative. The 64 GPU / 2048^3 FP64 runs also carry 512^3 plain-FP64

### Census verdict: the 512^3-tile FP64 failure IS the uint32 wrap (2026-09-18)

One Sedov step, 8 GPUs, mesh (2,2,2), FP64, `scaling/repro/fp64_wrap_census.py`.

blocks meet, so every seam carries the strongest gradients in the problem.
Sedov is symmetric, so each momentum component must sum to EXACTLY zero.

| N | per-GPU tile | field-4 offset | kernel | sum(mom_x) | sum(E) |
|---|---|---|---|---|---|
| 512 | 256^3 | 2^29 | plain | 0 | 5.43967753840555954e+09 |

| 1024 | 512^3 | 2^32 | fused | 0 | 4.35174203072444839e+10 |

At 256^3 and 384^3 tiles the two kernels agree BITWISE and the symmetry is
exact. At 512^3 tiles, and only there, the plain kernel breaks the momentum
symmetry and its total energy differs from the fused control by 6% after a
SINGLE step. The seam structure is identical in all six runs, so seam
non-conservation (item 4) cannot explain it; the only thing that changes is
whether field 4's byte offset lands on 2^32. That is the wrap, confirmed
independently of docs/history/JUPITER.md:44.

- The 64 GPU / 2048^3 FP64 throughput points (July 63 134, 2026-09-18 63 906)
  carry 512^3 plain-FP64 shards, so the STATES behind them are corrupt. In
  practice this costs nothing: those runs exist ONLY to produce scaling numbers
  (Uli, 2026-09-18), and the rate is unaffected -- same grid, same fixed 30
  steps, same flux evaluations, so the work done is identical whatever the
  values are. The rule is simply that no PHYSICS may be quoted from a
  512^3-tile plain-FP64 run, which nobody was doing.
- The positivity verdict is NOT sufficient: all six runs, including the two
  corrupt ones, report no negative density and no non-finite value. The census
  now also prints the symmetry residual, which is what actually caught it.
- A CAVEAT on the bitwise agreement at 256^3/384^3: it is one step. A single
  step may be too few to expose a seam inconsistency, since the second ghost
  layer only matters once gradients reach it. This is evidence that item 4 did
  not bite here, not proof that it never bites.

## 19. RETRACTED: "the time integration is 1st order" -- it is 2nd order

This section previously claimed, with measurements, that the scheme is 1st
order in time. THAT CLAIM IS WRONG and the error was in the method, not the
code. Kept rather than deleted because the way it went wrong is instructive.

**The mistake:** I measured the order by refining dt at FIXED dx, against a
same-grid dt->0 reference. That is a valid measurement for a method-of-lines
scheme and MEANINGLESS for MUSCL-Hancock, which is Lax-Wendroff-type: its
2nd-order-in-time term is built from SPATIAL derivatives (Cauchy-Kovalewski),
scaled by dt/dx. For linear advection, unlimited MUSCL-Hancock reduces
algebraically to Lax-Wendroff, whose dt^2 correction reproduces the Taylor
term only to O(dx^2). Measured against the semi-discrete limit at fixed dx the
residual is therefore O(dt * dx^2) -- genuinely 1st order in dt, with a dx^2
coefficient, which is why the absolute errors were tiny. Shrink dt at fixed dx
and plain Lax-Wendroff likewise collapses to forward Euler on central
differences.

**The correct test** refines dx and dt TOGETHER at fixed CFL against a known
solution. Linear acoustic wave, eps=1e-4, CFL 0.25, exactly N steps at
resolution N so dt halves precisely, L1 vs the analytic wave:

| refinement | minmod | unlimited centred |
|---|---|---|
| 32 -> 64 | 3.53 | 4.23 |
| 64 -> 128 | 3.67 | 3.47 |

Ratios cluster on 4: **2nd order, as designed.** minmod sits just under, the
expected cost of clipping a sine's extrema. This also agrees with the repo's
own soundwave convergence figure, which refines both together.

**What survives:** (1) the sec.8 "2nd-order time" doc entry is NOT an
overclaim for the hydro and should be struck from that list; (2) because the
scheme's time accuracy is coupled to dx rather than being an independent time
integrator, the Strang split of the sources CANNOT be judged by refining dt
alone either -- the meaningful question is the error at the CFL actually run,
where it measured 5x better; (3) the Euler/RK2 controls remain valid and are
worth keeping as a harness check.

**Lesson:** before measuring an order, establish which refinement path the
scheme is designed for. A confident measurement of the wrong quantity is worse
than no measurement, and this one was committed before it was checked.

## 25. Frozen Config, the command line, the run scripts (2026-09-20)

assemble/evolve branch went into main as c72b85a (10 commits) and this
follows it.

**Config is frozen.** `@dataclass(frozen=True)`; a run records in run.json
the object it ran with. The seven places that assigned to a config after
construction are gone: the two IC builders that resized the transverse grid

### `test_poisson_bidiff`: fixed, a solver-tightness mismatch

`solve_poisson_fmg_diff` floors its cycle counts (2 per level, 12 extra for
the periodic null space) precisely so forward and adjoint are tight enough for
FD-correct gradients; `solve_poisson_fmg_bidiff` passed the caller's (1, 1)
straight through. The two reverse-mode gradients then differed by 1.0076e-3
against a 1e-3 bound -- not a wrong rule, a looser solve. Both now use the
same floors, through one `_cycles()`, and the test passes.

### `test_poisson_adjoint` (Neumann): what it is NOT

The Neumann halo is singular on the constants exactly as the periodic one is,
so the obvious candidate was the gauge: `poisson_diff` pinned Φ's mean and
projected the cotangent for boundary 0 only. Extending that to boundary 1/2
moved the gate the WRONG way, 2.82e-3 -> 4.06e-2, so it was reverted with the
measurement recorded in the code. The null space is not the mechanism; what
is left is the discrete operator's adjoint at the Neumann boundary (the
reviewer's suspected boundary layer, sec.11). Next step: compare the
custom-vjp gradient against an explicitly transposed one-level operator on a
4^3 box, where the whole matrix can be written out.

### The turbulent-cooling inversion never had a cooling term

Bisecting the 61% gradient gap (sec.24) found no autodiff defect at all. The
`Driven-Turbulence-3D` IC hard-coded `rho = p = 1` code unit and IGNORED the
state its run scripts compute and print. Measured in the cooling setup: the
box runs at **T = 72.7 K** against `cooling_T_floor = 1e4 K`, so every cell
clamps to the floor on the first call, the map is constant, and
d(sum E)/dE is EXACTLY zero -- AD and FD agree on zero. The sub-step cap is
also exceeded 127x (2034 needed, 16 allowed) at the configured dt. There was
no cooling gradient to be 61% wrong about; the composed rollout's error came
from somewhere else and the cooling block contributed nothing.
Fixed: `turb_rho0` / `turb_P0` are Config fields (defaults 1, 1 = the old
behaviour), the IC reads them and the four turbulence scripts pass what they
already compute.

collects run scripts by filename, and this checkout carries five GITIGNORED
local scripts that exist in no other. One is a run script, and it still had
pre-move imports (converted in place, along with four others and a movie
renderer). The gate now enumerates the TRACKED set, which is also exactly
what CI sees, with a case that drops an untracked script beside the real ones
and asserts it is ignored. Lesson for the next big rename: a worktree cannot
see what only the working checkout has, so the first post-merge run IS a test.

## 27. The autodiff stack and the radiation solver (2026-09-21)

Two items the audit had left standing: the adjoint was known to work and
nobody could say what it cost, and `luna/radiation/m1.py` was listed as dead
code with no test and one caller in one person's checkout. Both are closed
here; `docs/AUTODIFF.md` is the reference, `docs/bench/` the numbers.

**The identity gates.** `tests/test_autodiff_identities.py` (11 tests) checks
what needs no reference value: the transpose identity for the hydro step and
for both Poisson boundaries, gradient identities that follow from
conservation, linearity, the chain rule, and the two places the step is only
piecewise differentiable. `tests/test_autodiff_validation.py` adds finite
differences (floor 6.2e-7), the custom VJP against unrolled AD, and a teeth
check that a corrupted adjoint fails the identities.

**The Neumann adjoint was right and the test was wrong.** The pure-Neumann
Laplacian is singular; its null space is the constants and it solves only
sources that sum to zero. A one-voxel FD bump leaves that subspace, and the
mismatch came back as a constant 7.74e-5 at every voxel -- the null space
itself. Probing `e_i - mean(e_i)` brings it to 6.5e-8..1.1e-5.
`tests/test_poisson_neumann_matrix.py` builds the operator as a matrix and
confirms symmetry and the pseudo-inverse independently.

**The M1 solver had a NaN waiting in its gradient.** `|F| = sqrt(sum F_i^2)`
has an infinite derivative at F = 0 and reverse mode turns that into NaN: the
gradient of a beam was finite in the four cells the front had reached and NaN
everywhere ahead of it, while the forward pass was clean, because the
division by |F| was floored and the square root was not. Also: the substep
ceiling charged an extra transport substep whenever the ratio landed on an
integer (3*0.1/(0.4*0.01) = 75.00000000000001).

**Radiation is a stage now** (`luna/sources/radiation.py`, `Radiation` in
`luna/sources/stages.py`, 20 config fields). The coupling is exactly
conservative cell by cell -- the force hands the gas the momentum the opacity
took out of the flux and pays for the work out of the radiation energy;
absorption and emission use the exact exponential -- so the gate asserts on
totals at round-off, not on a tolerance. The multi-GPU path is the hydro's
own ppermute halo injected into the transport, not a second implementation,
and agrees with the single-device answer to 1e-12 on 8 virtual devices.
Restart with radiation is refused: checkpoints do not carry the field.

**What a gradient costs** (one MI300A, FP64, three reps after compile).
grad/forward is 2.3 for hydro at 64^3 and 5.3-5.4 at 128^3 and 256^3, flat in
rollout length; 2.8-3.0 for the implicit gravity adjoint; 4.2-5.6 for
radiation. Memory grows slowly with length and fast with size: 16 steps of
hydro at 128^3 peak at 3.74 GiB against 2.41 GiB for one. The longest hydro
rollout that still differentiates at 128^3 is 255 steps (bisected) at 22.4
GiB. Two devices give 2.00x on the 256^3 gradient with half the peak memory.
Radiation is the expensive one: 20.6 GiB at 128^3 against 3.1 GiB for hydro,
and the coupled gradient at 256^3 does not fit (XLA asks 133 GiB of 104.5).
Rematerializing the radiation half-step (`rad_remat`, default on) cuts a
third of that for 9-11% more time.

**Two measurement bugs in the benchmark itself, both mine, both recorded.**
The driver told each child which GPU to use with an absolute
`HIP_VISIBLE_DEVICES=0`, which inside an allocation holding GPUs 2-3 on a
shared node selects another job's device: four SIGSEGVs and a set of timings
taken on a contended GPU, all discarded. And the jobs let JAX preallocate a
fraction of "device memory", which on an APU IS the node's RAM, straight
through the cgroup limit.

**The stack was not the pinned stack, and the pinned one is better
(same day, later).** `requirements.txt` pins jax 0.10.1; the venv every run in
this campaign used is 0.10.0, the version this audit records as segfaulting in
AD. A sibling venv settled it -- `venv_jax_rocm7.2_j1011`, same
packages at 0.10.1, no mpi4py/mpi4jax. On 0.10.1
`tests/test_sedov_gradients.py` PASSES in 70 s where 0.10.0 segfaults, the
coupled MUSIC blocks test takes 21 s (0.10.2: >2700 s), the fast tier is 28/28
in 84 s and 27/27 on two devices, and the autodiff and radiation files pass.
So sec.26's worry is resolved in the other direction: the pin is right, the
environment was wrong, and nothing needed 0.10.2. The pin comment in
`pyproject.toml` now records the measurement instead of the open question.

**The radiation gradient crash is an async-dispatch race, not autodiff.** It
happens on 0.10.0 AND 0.10.1, on the second or third execution of the
compiled reverse-mode program, with memory flat (2.6 GiB of a 104.5 GiB
limit at 64^3), while the forward pass of the same rollout runs indefinitely.
Disabling XLA command buffers helps at one size and not another; disabling
autotuning does not help. `HIP_LAUNCH_BLOCKING=1` fixes it, and so does
`AMD_SERIALIZE_KERNEL=3`: the rollouts that die without it survive every call
with it, at 64^3/8, 64^3/16, 128^3/8 and coupled 128^3/8. It is the second
time LUNA has hit this on the adjoint path (the multi-GPU IC inversion needed
the same variable). The cost is free for the hydro and the radiation and
3.1x for the multigrid, which is the part of this worth remembering:
gradient seconds async -> serialized, radiation 128^3/4 0.583 -> 0.570,
radiation 64^3/4 0.0881 -> 0.0844, hydro 64^3/8 0.0123 -> 0.0122, hydro
128^3/8 0.0764 -> 0.0760, hydro 256^3/8 0.5786 -> 0.5786, but gravity 128^3/8
0.509 -> 1.569 (and 1.762 with AMD_SERIALIZE_KERNEL). A long chain of small
kernels is what serialized launches punish. There is a free mitigation that
is not general: making the radiation program smaller fixes it with the
launches async -- at 128^3/8 steps rad_substeps=1 survives at 0.445 s per
gradient and rad_order=1 at 0.524 s, where the default dies -- and turning
XLA command buffers off saves 64^3 at no cost but not 128^3. Fewer groups
and remat off change nothing, so the trigger is the SIZE of the program, and
the coupled case dies even at one substep because the multigrid's own
instructions add to it. So no single switch is right for every run;
`setup_radiation` warns and names the options, and the real fix is to make
the transport emit fewer instructions (the axis loop, the RK2 stages and the
substep scan multiply out), which speeds the gradient up as well.

**Superseded: the open item as it stood before those two runs.** `requirements.txt` and
`pyproject.toml` pin jax 0.10.1; the venv every run in this campaign used is
0.10.0, the version this audit already records as segfaulting in AD. The
radiation gradient at >= 8 steps dies with SIGSEGV, usually on its third
execution, with memory flat and far from the limit, while the forward pass of
the same rollout is stable -- and on the same venv
`tests/test_sedov_gradients.py` segfaults as well. So the crash is consistent
with the known 0.10.0 bug, the pinned 0.10.1 has never been installed here,
and 0.10.2 (which fixes it) still carries the 160x cosmology regression from
sec.26. Next: install 0.10.1, rerun the radiation rollouts and
`test_sedov_gradients` against it, and decide the pin with three data points
instead of two.
